# 群组对话：多角色文字交流与后续群组通话

Status: draft

本计划只描述一个 feature：群组对话。它是现有单角色「对话」之外的新领域实体，不把 `Conversation` 偷换成含糊的群聊。当前 `GLOSSARY.md` 把「对话」定义为用户与单个角色的交流，并把「群聊」列为避免用词；票 01 已采用「群组对话」「群组成员」「群组消息」「群组回合」「群组通话」并写入 `GLOSSARY.md` 与 ADR-0029，后续只在新决策出现时增补。

## Problem Statement

- 用户现在只能分别和一位角色交流，不能自己选几位角色放在一个共同记录里。
- 现有 `Conversation`、`Message`、`ConversationEngine`、`Call` 和前端 `LiveConversation` 都把一个记录绑定到一个 `character_id`。直接给这些类型加可选角色会破坏历史、好感度、记忆、统计、数据包和通话的既有语义。
- 角色的主动发言、消息引用、`@` 目标和多角色语音没有现成的记录或传输协议。当前搭话是单角色当前对话的独立记录，不能直接复用成群内消息。

## Solution

群组对话拥有独立的 id、成员顺序和消息记录；旧单角色 API、数据库表和页面保持兼容。用户创建群组并手动选择角色，群组页展示群头像、成员和带作者的消息。首个可上线的文字纵切只允许一个明确的角色回复：用户回复某条角色消息，或使用 `@` 指定一位当前成员；没有唯一目标时返回提示，不猜测、不同时唤起多人。

角色的提示词包含当前成员列表、群组最近历史和被引用的消息。成员名单与安全规则放在 system 上下文；历史消息放在明确分隔的 user 上下文中，并用作者标签标注为“不可信历史”，消息正文不能改变系统规则，也不能让模型读取别的群组。

主动发言与群组通话分开实现：先做用户触发的单角色回复，再做有上限的群内自动跟话，最后才做群组通话。真正的离线主动搭话、推送和多角色同时说话不进入第一版。

本文阶段编号对应实现票：P1 为术语、契约和数据层；P2 为明确目标的文字纵切；P3a/P3b 为轮流与有限追加回复；P5 为群组通话；P6 为数据包、统计、记忆和文档收尾。

## 需要修改的原始设想

1. **“切换到角色的模型”需要改名。** 当前项目的扮演 LLM 是部署级配置，没有每位角色一套 LLM；角色独有的是 `voice_id`、头像、印象色和立绘。群组通话应切换当前发言角色的音色、头像和立绘。若产品确实需要每角色独立 LLM，应另开需求，不在本计划中暗中引入。
2. **“角色比较积极主动”需要有边界。** 无限制的角色互相回复会造成循环、费用和刷屏。第一阶段只在用户回合里生成一个指定角色；后续最多追加一个由调度器选出的角色，且一个群组回合结束后不再自动接龙。离线主动搭话要另做群级调度、未读和轮询/推送。
3. **`@` 和引用不能只靠前端文字解析。** 服务端保存规范化的角色 id，并验证角色仍是当前成员；引用目标、`@` 目标冲突时拒绝请求。
4. **群组通话不是文字功能的附带 UI。** 现在一次通话只创建一个 TTS 管线和一个角色音色，必须新增 speaker 事件和服务端音色切换协议；因此群组通话排在文字功能稳定之后。
5. **单角色能力不能默认复制到所有成员。** 好感度、冷却、结束对话、礼物、照片、搭话、成就、按角色统计都要求重新定义归属。文字 MVP 暂不启用这些能力，避免一条群组消息被隐式算成多位角色的回合。

## User Stories

### 群组生命周期

1. 作为用户，我想从角色列表中选择至少两位角色创建群组对话，这样她们共享一份记录。
2. 作为用户，我想在群组页看到当前成员、成员顺序和派生的群头像，这样我知道谁在群里。
3. 作为用户，我想添加或移除成员，移除后历史消息仍保留作者，之后不再让已移除角色回复。
4. 作为用户，我想看到独立的群组列表和最后一条消息，单角色对话列表的排序和语义不被改变。

### 文字交流

5. 作为用户，我想发送一条文字并回复某条角色消息，角色能看到引用目标和群组历史。
6. 作为用户，我想使用 `@` 指定一位当前成员，只有她先回复。
7. 作为用户，我想看到每条角色消息的头像、名字、印象色和时间，能区分连续发言者。
8. 作为用户，我想在角色回复失败时看到错误且不留下半条消息；重试不会重复写入同一个群组回合。

### 主动回复与通话（后续阶段）

9. 作为用户，我想在没有明确 `@` 时由确定性的轮流规则选择一位角色回复，而不是随机唤起多人。
10. 作为用户，我想在群组通话拨号和没有角色说话时看到群头像；角色开始回复时切换到她的头像、立绘、字幕和音色。
11. 作为用户，我想在通话中切换页面仍保持同一通群组通话，符合 ADR-0018 的导航外壳规则。

## Implementation Decisions

### 1. 领域边界和不变量

- 新增 `GroupConversation`，只属于创建它的一个用户；不支持多人用户共享、邀请链接或跨用户实时协作。
- 群组首期要求 2–5 位不同角色，成员有稳定顺序。5 是为提示词长度、费用和未来音色切换设的初始上限，不做部署配置项；使用一段时间后再凭数据调整。
- 创建、加成员、移除成员、删除群组都必须通过 `user_id + group_id` 鉴权。通话或群组回合进行中不允许改成员。
- 移除成员采用软移除：历史作者仍显示，当前成员列表不再包含她，也不能成为新回合目标；首期不允许移除到少于两位当前成员，需要清空时删除整个群组。角色从部署配置下线时，历史保留作者快照，群组页显示不可用成员，不把整个群组变成不可读。
- 群头像不保存图片，按成员顺序由前端用现有头像派生拼贴；成员变化后更新。通话开始时固定一份成员快照，避免通话中换头像与 speaker 状态互相覆盖。
- 群组只有一条连续记录，不采用单角色的 current/past conversation 规则；删除群组就是删除整段群组历史。
- 群组名称首期由用户填写或由成员名派生，不调用后台模型生成标题。重命名可在成员管理票中一并支持，但不影响模型上下文。

### 2. 存储：新增表，不改旧单聊表

在 `backend/src/eidolon/group_store.py` 新建 `GroupStore`、数据类和 SQL；不要把旧 `conversations.character_id` 改为可空，也不要给单角色 `messages.role` 加第三种作者。建议形状如下：

- `group_conversations`: `id`, `user_id`, `title`, `created_at`, `updated_at`。
- `group_members`: `group_id`, `character_id`, `position`, `added_at`, `removed_at`, 以及用于保留历史显示的 `name_snapshot`。
- `group_messages`: `id`, `group_id`, `turn_id`, `author_kind`（`user|character`）、`author_character_id`、`author_name_snapshot`、`text`、`ja`、`zh`、`segments`、`created_at`、`reply_to_message_id`、规范化的 `mentions` JSON。角色消息继续保存 delivery cues，显示时遵守 ADR-0007。
- `group_turns`: `id`, `group_id`, 客户端幂等键、开始/结束时间和状态。它把一条用户输入及其一个或多个角色回复归在一起，供并发、限额和重试使用；成员版本和复杂 planner 状态留到需要时再加。

所有表都用现有 `IF NOT EXISTS`/增量建表方式兼容旧 SQLite。把表加入 `backend/src/eidolon/database.py` 的 `USER_DATA`、按群组删除清单和账号删除清单；由 `assembly.py` 构造并注入 `GroupStore`，再由 `app.py` 注册群组路由。备份自然随整库包含。`GroupStore` 的公开方法保持 async，SQL 只在数据库访问层执行，遵守 ADR-0028。

同一群组同时只能有一个进行中的群组回合：事件循环上的 per-group lock 负责快速拒绝，写事务再次校验幂等键和最后消息。不同群组仍可并行。角色回复失败时不写角色半条消息；P2 的用户消息和单个角色回复一次事务提交，P3 追加角色消息可以各自失败而不回滚已经完成的主回复，并在前端标明该回合部分完成。

### 3. 后端接口和文字纵切

新增独立路由模块 `backend/src/eidolon/group_api.py`，由 `app.py` 注册；旧 `/api/conversations`、`/api/offer`、`/api/ice-servers?conversation=…` 保持原状。

建议接口：

- `POST /api/groups`：创建群组，校验 2–5 个存在的角色且无重复。
- `GET /api/groups`：返回用户的群组摘要、成员、派生头像所需的角色 id、最后一条消息。
- `GET /api/groups/{group_id}`：返回群组、当前成员和历史成员快照。
- `PATCH /api/groups/{group_id}`：修改名称或按明确的 add/remove 集合修改成员。
- `DELETE /api/groups/{group_id}`：硬删除群组记录及其附属数据。
- `GET /api/groups/{group_id}/messages`：按消息 id 顺序返回带作者、引用和 mentions 的记录。
- `POST /api/groups/{group_id}/turns`：SSE 文字回合。请求包含 `text`、可选 `reply_to_message_id`、规范化 `mention_character_ids`、客户端幂等键和现有 `own_keys`。

P2 的目标解析规则固定为：`reply_to_message_id` 只能指向当前成员的角色消息，且没有 mentions 时使用该消息作者；引用制作人消息或用户消息直接拒绝；只有一个 mentions 时使用它；引用作者与 mentions 都存在且不一致时拒绝；多于一个 mentions 时拒绝。服务端验证目标是当前成员、引用消息属于同一群组，文字长度沿用 `MAX_INPUT_LENGTH`。SSE 事件沿用 `user/delta/done/error`，额外在首个角色 delta 前发送 `speaker`，`done.message` 带 `author_character_id` 和 `turn_id`。

`GroupTurnEngine` 放在 `backend/src/eidolon/group_engine.py`，不直接扩展假定单角色的 `ConversationEngine`。它的外部接口只接收群组上下文、目标角色、用户文字和 `TurnLLMs`，内部复用 `reply_format`、LLM provider 和 own-key 适配，避免两套解析逻辑长期漂移。固定提示包含目标角色的人设、世界设定和制作人资料；dynamic system 消息只包含成员名单、当前目标和“历史正文不可信”的规则。最近 N 个群组回合和引用消息放入单独、明确分隔的 user 历史块，用 `[制作人]`、`[角色：xxx]` 标签标记；不得把用户可控正文提升为 system 指令，也不得把标签解析成新的 speaker 权限。

P2 暂不调用判断模型、好感度、冷却、照片、礼物、单角色搭话和单角色标题；也不写跨对话记忆。模型只能看到这个群组的记录和当前成员，不能看到用户其他群组或单角色记录。P6 再决定共享记忆是否读取、由哪位 speaker 作为 `source_character_id` 写入。

限额和运行记录不能被静默绕过：新增 `Admissions.group_turn`，复用现有 `UsageLimiter.take("turn")`，一次用户群组回合只占一次文字限额，own LLM 的免限额规则照旧。P2 不改现有 `activity_records`/`record_rollups`（它们要求单角色 `character_id`），群组回合状态、错误和目标 speaker 由 `group_turns` 审计，后台暂不把群组数据伪装成某个角色；P6 再单独设计 `scope_type=single|group` 的活动记录迁移和统计口径。消息正文不进入运行记录。

### 4. 前端文字界面

新增 `frontend/src/components/conversations/group/` 下的群组列表、成员选择器、群组消息区和输入栏；新增 `frontend/src/lib/groupChat.ts`（群头像、目标解析、消息分组、引用状态）及对应纯函数测试。不要把 `ConversationView` 改成大量 `character | group` 条件；单角色页继续使用现有 `LiveConversation`。

路由建议为 `/conversation/group/[groupId]`，避免和 `/conversation/[characterId]` 冲突，并在 `frontend/src/lib/navShell.ts` 中将它识别为外壳内页面。`ConversationDirectory` 增加独立的 groups 状态和刷新入口，单角色目录 key 与通话状态不改变。群组列表提供“创建群组”，选择至少两位角色后跳转群组页；成员管理入口在群组页首。

消息 UI 使用现有 shadcn/Base UI、Tailwind v4 和 `DESIGN.md` 的 token 规则：用户消息和角色消息保持现有布局语言，角色消息显示头像、名字、印象色和引用卡；连续同一 speaker 可合并视觉分组，但不能丢作者字段。所有新文案加入 `frontend/src/i18n/zh.ts`，图标从统一别名文件导出，不直接散用 Lucide 原名。群组颜色只用现有 `herVars` 规则；群头像不新增固定颜色。

输入栏的 `@` 菜单和“回复”操作只负责生成角色 id 与引用 id，正文里的 `@` 只是展示文本。发送期间锁定成员修改和第二次提交；SSE 的 `speaker` 事件驱动消息头像，失败时按现有错误卡显示。

### 5. 主动回复的分期设计

- P2 只允许明确目标的一位角色回复，保证行为、计费和提示词都可预测。
- P3a 支持无目标文字：按群组成员顺序轮流选择一位当前成员回复；每个用户群组回合仍只有一位主 speaker。
- P3b 才考虑“主 speaker 之后再主动接一句”：最多一位追加 speaker、固定总消息数和总超时、每个回合只调度一次，不允许角色回复触发下一轮角色回复。追加消息失败不重试、不污染已完成记录。
- 任何离线生成都需要群级 schedule、每日上限、未读标记和前台轮询；在这些接口存在前不复用 `reach_outs`，也不把角色主动消息伪装成单角色搭话。

### 6. 群组通话（独立后续阶段）

群组文字协议稳定后再新增 `GroupCall`/`GroupCalls`，不修改单角色通话的默认路径。通话请求携带 `group_id`，接通时快照成员；同一用户仍只能有一通通话，限额按一通群组通话计算。

- 拨号、用户说话、没有角色回复时显示派生群头像。
- 服务端在每段角色语音前发送 `speaker-started {speaker_id}`，在该回复结束后发送 `speaker-ended`；前端 `CallLayer` 只依事件切换头像、颜色、立绘和字幕，音频始终是一条 WebRTC track。
- 服务端按 speaker 的 `voice_id` 创建或切换 TTS 会话，角色只能串行说话。切换不成功按服务失败结束当前回合/通话，不在浏览器悄悄换成另一位角色的声音；切换完成前保持群头像。
- `ConversationDirectory`/`NavShell` 继续持有通话，沿用 ADR-0018 的换页不断线和离开确认；新增 group call target 的 union 分支，不破坏单角色 `characterId` 分支。
- 群组通话首版不启用按角色好感度、冷却、结束对话、照片、礼物和立绘情绪累计。多角色同时发声、跨角色独立 TTS 并行和跨标签页通话列为后续原型。

### 7. 删除、导出、统计和文档收尾

- 账号删除、群组删除、数据库备份必须覆盖首期四张群组表（`group_conversations`、`group_members`、`group_messages`、`group_turns`）和后续 `group_calls`；删除后不留作者、引用或消息正文。
- 在 `backend/src/eidolon/data_package.py` 和格式文档中增加群组类别与版本迁移，导出成员快照、消息作者、引用、mentions、标题和通话记录；旧包继续导入，新包被旧版本明确拒绝。若 P6 尚未完成，群组功能不得静默排除在导出之外，应明确阻止导出或显示未支持错误。
- `stats.py`、`achievements.py`、`memory.py` 和后台看板在口径确定前只按现有单角色数据工作；P6 决定群组回合/通话是否进入总数、是否按 speaker 拆分，以及共享记忆的来源角色。不得把群组数据伪装成某一位角色的单聊。
- 更新 `GLOSSARY.md`、必要 ADR（群组独立实体、群组回合计费、群组 speaker/TTS 协议）、`DESIGN.md`、隐私政策、数据包格式和 README。实现票按仓库风格使用 `docs:` 计划/拆票、`feat:` 功能、`fix:` 审查修复；本轮不创建 `.scratch` 票、不提交。

## Testing Decisions

测试只穿过对外接口或一个清晰的群组引擎 seam，不复制内部 SQL 细节。

### 后端

- `GroupStore`：旧库启动建表、创建/成员顺序/软移除/历史作者快照、权限隔离、群组硬删除、账号删除和不同群组并发。
- HTTP：创建数量边界、重复/不存在角色、移除成员、群组 id 越权、引用跨群、mentions 非成员、冲突目标、输入长度、幂等重试和忙碌群组。
- `GroupTurnEngine`：提示词包含成员和最近历史；消息作者标签不被当作系统指令；单 speaker 角色输出带 author id；失败不落半条消息；相邻历史在所有 LLM 协议下都保持可解析。
- `Admissions.group_turn`/`group_turns`：一次用户回合只计一次，own LLM 免限额，失败与用户离开按现有语义结算；P2 不接现有 activity/看板，P6 再测统一 scope 迁移且不泄露正文。
- P3 planner：无目标轮流顺序、最多一次追加 speaker、总超时、去重、没有递归角色回合；离线主动功能另测 schedule 和未读。
- P5 通话：`speaker-started/ended` 顺序、TTS 切换失败、群头像回退、单条音轨、通话限额/统计和 ADR-0018 的挂断规则。复用 `test_call*.py` 的 fake speech/RTC seam，不接真实服务。
- P6：数据包版本兼容、群组删除和账号删除、统计/看板口径。涉及接口返回独有字段时，按 `docs/agents/implementing.md` grep 并运行受影响的测试。

### 前端与本地验收

- `frontend/src/lib/groupChat.test.ts`：目标优先级、引用/mentions 校验、群头像成员顺序、消息分组、speaker 状态和失败恢复。

## Out of Scope

- 多用户共享群组、邀请链接、跨用户实时协作和跨标签页同步。
- 消息编辑、撤回、删除、搜索、已读回执、贴图和群公告。
- 首期离线主动搭话、Web Push、邮件和主动来电。
- 无限角色互相接龙、同时多角色发声、跨角色并行 TTS、每角色独立 LLM。
- 在没有明确规则前，把好感度、冷却、结束对话、礼物、照片、记忆、成就、统计和单角色标题复制到群组。

## Further Notes

### 推荐实现顺序

1. **术语与契约**：票 01 已确定「群组对话」词汇、2–5 成员边界、群名/头像派生、成员移除、删除和首期数据包承诺；后续仅在决策变化时补 GLOSSARY/ADR。
2. **数据层与生命周期**：新增 `GroupStore`、四张首期表、账号删除/群删除、群组列表/成员 API；此票不调用模型。
3. **文字纵切**：新增 `GroupTurnEngine`、群组回合 admission、SSE speaker 事件、群组页和最小前端消息展示；只支持明确指定的一位角色。
4. **引用与 `@`**：加入结构化 mentions/reply-to、引用卡、目标冲突校验、幂等和群组串行锁。
5. **用户触发的主动回复**：无目标轮流 speaker，再评估最多一条追加回复；写明每日/每回合上限和失败策略，不复用单角色 reach-out。
6. **群组通话原型与实现**：先做服务端 speaker/TTS seam 和事件协议，再接导航外壳、群头像、立绘和本地验收；复杂多方通话另开计划。
7. **数据与产品收尾**：数据包、统计、成就、记忆、隐私政策、README、`DESIGN.md`、后台运行记录和完整 Playwright 验收。

### 开工前需要用户确认的决策

- 是否接受把规范名称定为「群组对话」，用户界面是否仍在必要处显示更口语的「群组」；不建议继续把现有单角色「对话」直接叫群聊。
- 是否接受首期 2–5 位成员、删除成员只影响未来回复、群名不由模型自动生成。
- 是否接受没有 `@`/引用时首期拒绝发送，随后再做轮流 speaker；这能避免第一版随机花费和错误回复。
- 是否接受群组文字首期不改变好感度、记忆、礼物、照片、搭话、成就和单角色统计，并按一次用户群组回合计一次文字限额。
- “角色模型”是否确实指音色/立绘；若要每角色独立 LLM，应先补独立的模型配置需求。
- 群组数据包是否要求首版就能导出/导入；若要求，P6 必须先于公开开关，否则应阻止导出而不是静默丢数据。

### 兼容和回滚

- 所有群组表、路由和前端模块都可独立关闭；旧单角色表和 API 不迁移、不重命名。旧前端遇到群组入口前应由服务端/部署开关隐藏，避免旧客户端误读新消息。
- 每个阶段先以独立接口上线，再开放入口；SQLite 建表向前兼容，回滚代码时保留空表不影响旧功能。公开群组前必须完成账号删除、备份和数据包策略。
