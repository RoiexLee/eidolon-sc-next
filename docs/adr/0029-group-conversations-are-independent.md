# 群组对话是独立实体，首期只做明确目标的文字回合，群组通话后置

现有 `Conversation` 和 `Call` 都把一条记录绑定到一个角色。把它们改成可选的单角色或群组，会改变历史记录、作者、限额、好感度、记忆、统计和通话的既有语义。因此群组对话拥有独立的实体、成员、消息和回合；旧的单角色 `Conversation`、`Call` 及其接口保持原状。

群组对话只属于创建它的一个用户，首期有两至五位不同的当前成员，并保留成员顺序。移除成员只影响之后的目标选择，历史消息仍保留作者快照。首期文字回合必须由用户明确指定一位当前成员回复；没有唯一目标时拒绝，不随机选择或同时唤起多人。

这里所说的角色模型，指角色的音色、头像和立绘，不是每位角色独立的一套 LLM。群组通话需要 speaker 事件和服务端音色切换，等群组文字协议稳定后另行实现；它不会改变单角色通话的默认路径。数据包不要求在首期支持群组导出，格式和迁移留给后续票处理，未支持时不得静默丢弃群组数据。

## Considered Options

- **把 `Conversation` 扩展成单角色或群组**：调用方要在每个历史、作者、好感度、记忆和统计路径上判断可选的角色，旧数据语义也会被改写。
- **把群组当成多个单角色对话的组合**：无法表达一条共享历史、引用和作者，也会把一条群组回合错误地记成多位角色的单聊回合。
- **首期直接实现群组通话和多角色 LLM**：需要新的 speaker/TTS 协议和角色级模型配置，范围与风险都超过文字契约。

## Consequences

- 新功能使用独立的 `GroupConversation` 领域实体和群组路由、存储；单角色数据表和 API 不迁移、不重命名。
- 首期群组文字行为可预测、每回合只有一位明确目标的 speaker；轮流回复、主动接话和多角色发声另行设计。
- 群组通话上线前必须先定义 speaker 事件、音色切换和成员快照，单角色通话继续遵守现有契约。
- 首期不把数据包导出作为群组上线条件；后续数据包票必须决定版本兼容、导出内容和未支持时的明确阻止方式。
